# Feature 0055: GPT-5 Reasoning Model Support for Entity Extraction

## Overview
Add support for GPT-5 reasoning models (gpt-5-mini, gpt-5-nano, gpt-5, gpt-5-pro) in the entity extraction pipeline. These models use different API parameters than GPT-4 models and require longer timeouts due to internal reasoning phases. The system must dynamically detect the model type and apply appropriate parameters and timeouts.

## Problem Statement
Current entity extraction fails with GPT-5-mini because:
1. Uses `max_tokens` parameter (GPT-4 style) instead of `max_completion_tokens` (GPT-5 requirement)
2. Passes unsupported parameters (`temperature`, `top_p`, etc.) that GPT-5 models reject
3. Uses 30-second timeout insufficient for reasoning models (need 120-180s)
4. Results in: "Request timed out" errors and empty chunks during document processing

## Model Detection Strategy
Reasoning models include: `gpt-5*`, `o1*`, `o3*`, `o4*`
Standard models include: `gpt-4o*`, `gpt-4-turbo`, `gpt-3.5*`

Detection pattern: `model.startswith(('gpt-5', 'o1', 'o3', 'o4'))`

## Parameter Mapping Table

| Parameter | GPT-4 Models | GPT-5 Reasoning Models |
|-----------|-------------|----------------------|

## Implementation Algorithm

### Dynamic Parameter Construction
```
1. Extract model name from user settings
2. Determine if reasoning model:
   - Check if model starts with: 'gpt-5', 'o1', 'o3', 'o4'
3. Set timeout:
   - If reasoning: 180 seconds
   - If standard: 30 seconds
4. Build base parameters:
   - messages: [system_prompt, user_prompt]
   - model: selected_model
   - max_completion_tokens: 4000
5. If reasoning model:
   - Add reasoning_effort: "medium"
   - Filter kwargs to remove unsupported params
6. If standard model:
   - Include all kwargs (temperature, top_p, etc.)
7. Create AsyncOpenAI client with dynamic timeout
8. Call client.chat.completions.create() with filtered params
```

### Parameter Filtering Logic
```
1. Define unsupported_for_reasoning = {
     'temperature', 'top_p', 'presence_penalty', 
     'frequency_penalty', 'logprobs', 'top_logprobs', 'logit_bias'
   }
2. If reasoning model:
   - openai_kwargs = {k: v for k, v in kwargs.items() 
                     if k not in unsupported_for_reasoning}
3. If standard model:
   - openai_kwargs = kwargs (no filtering)
4. Always filter LightRAG-internal params (existing logic)
```

## Technical Notes

### Backward Compatibility
- `max_completion_tokens` works for both GPT-4 and GPT-5 models
- Older OpenAI SDK versions may not recognize `max_completion_tokens` but it aliases to `max_tokens`
- No breaking changes for existing GPT-4o-mini users

### Reasoning Tokens
- GPT-5 models generate hidden "reasoning tokens" before final output
- These don't appear in response but count toward usage
- Example: 6-phrase output consumed 1344 reasoning tokens + 47 completion tokens
- Longer timeouts necessary to accommodate reasoning phase

### Timeout Strategy
- Per-call timeout (30s → 180s for reasoning models)
- Document-level timeout remains 300s (inactivity timeout, not affected)
- Progress callbacks reset inactivity timer regardless of model type

### Error Handling
- OpenAI API already returns clear errors for unsupported parameters
- Existing error handling in `query` method (lines 456-464) handles parameter errors
- Timeout errors already handled by retry logic in LightRAG

## Affected Workflows

### Document Upload & Entity Extraction
1. User uploads document
2. `DocumentProcessor.extract_text()` extracts content
3. `RAGEngine.insert()` called with text
4. LightRAG calls entity extraction via `_create_llm_func`
5. Model type detected → parameters adjusted → timeout set
6. GPT-5-mini completes reasoning → returns entities → processing continues

### Chat Queries
1. User sends query
2. `RAGEngine.query()` or `query_stream()` called
3. Model type detected from settings
4. Appropriate parameters and timeout applied
5. Response generated and returned
