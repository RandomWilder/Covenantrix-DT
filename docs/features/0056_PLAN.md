# Feature 0056: Split Model Usage for Entity Extraction vs Chat Queries

## Overview
Optimize system performance by using different models for different operations: gpt-4o-mini for fast entity extraction during document processing, and user-selected model (including gpt-5-mini) for chat query responses. This leverages the strengths of each model type - fast pattern recognition for entity extraction and reasoning capabilities for chat responses.

## Problem Statement
GPT-5-mini is 5-10x slower than gpt-4o-mini for entity extraction because:
1. Generates 1000-1500 hidden reasoning tokens per chunk (30x token usage)
2. Takes 15-40 seconds per entity extraction vs 2-5 seconds with gpt-4o-mini
3. Entity extraction doesn't benefit from reasoning - it's straightforward pattern recognition
4. Document processing now takes 4-5 minutes vs 30-60 seconds with gpt-4o-mini

## Solution Strategy
Detect operation context (document processing vs chat query) and apply appropriate model:
- **Document insert operations** (entity extraction): Force gpt-4o-mini regardless of user settings
- **Chat query operations**: Use user-selected model from settings (gpt-5-mini, etc.)

## Expected Performance Impact
- **Entity extraction**: 30-60 seconds (10x faster than current)
- **Chat responses**: Maintains gpt-5-mini quality and reasoning
- **Cost**: 30x cheaper for entity extraction operations
- **No quality loss**: gpt-4o-mini excels at entity extraction tasks

## Implementation Algorithm

### Operation Context Flow
```
1. Document Upload:
   ├─> RAGEngine.insert() called
   ├─> Set self._current_operation_context = "entity_extraction"
   ├─> LightRAG processes chunks
   ├─> Each chunk calls _create_llm_func()
   ├─> Function detects context = "entity_extraction"
   ├─> Overrides model to "gpt-4o-mini"
   ├─> Fast entity extraction (2-5 seconds per chunk)
   └─> Reset self._current_operation_context = None

2. Chat Query:
   ├─> RAGEngine.query() or query_stream() called
   ├─> Set self._current_operation_context = "chat_query"
   ├─> LightRAG retrieves context
   ├─> _create_llm_func() or _create_streaming_llm_func() called
   ├─> Function detects context = "chat_query"
   ├─> Uses user-selected model (e.g., gpt-5-mini)
   ├─> Reasoning model generates thoughtful response
   └─> Reset self._current_operation_context = None
```

### Model Selection Logic
```
function determine_model_and_config():
    context = self._current_operation_context
    
    if context == "entity_extraction":
        return {
            model: "gpt-4o-mini",
            timeout: 30.0,
            is_reasoning: false,
            reasoning_effort: null
        }
    
    if context == "chat_query":
        user_model = self.user_settings["rag"]["llm_model"]
        is_reasoning = user_model.startswith(('gpt-5', 'o1', 'o3', 'o4'))
        
        return {
            model: user_model,
            timeout: 180.0 if is_reasoning else 30.0,
            is_reasoning: is_reasoning,
            reasoning_effort: "medium" if is_reasoning else null
        }
    
    # Fallback (shouldn't happen)
    return {
        model: "gpt-4o-mini",
        timeout: 30.0,
        is_reasoning: false,
        reasoning_effort: null
    }
```

## Technical Notes

### Thread Safety
- Instance variable `_current_operation_context` is set/reset within same async call
- No concurrent access issues - each document/query runs in sequence
- Existing semaphores already prevent concurrent RAG operations

### Backward Compatibility
- No changes to API contracts or settings
- Existing user settings remain unchanged
- Users who selected gpt-5-mini still get it for chat queries
- Only internal routing logic changes

### Model Override Transparency
- Users don't need to know entity extraction uses different model
- Settings UI still shows their selected model for chat
- No confusion about which model is being used

### Error Handling
- try-finally ensures context is always reset
- Prevents context "leaking" between operations
- If error occurs during insert/query, next operation starts clean

### Future Extensibility
- Operation context pattern can support additional contexts:
  - `"summary_generation"` - could use different model
  - `"question_answering"` - could use specialized model
  - `"code_generation"` - could use code-optimized model

## Affected Workflows

### Document Upload (Changed)
1. User uploads document
2. `DocumentProcessor.extract_text()` extracts content
3. `RAGEngine.insert()` called → sets context to "entity_extraction"
4. LightRAG processes chunks → calls `_create_llm_func()`
5. **Function detects entity extraction context**
6. **Overrides to gpt-4o-mini regardless of user settings**
7. Fast entity extraction completes (30-60 seconds total)
8. Context reset to None

### Chat Query (Unchanged Behavior)
1. User sends query
2. `RAGEngine.query()` or `query_stream()` called → sets context to "chat_query"
3. LightRAG retrieves relevant context
4. `_create_llm_func()` or `_create_streaming_llm_func()` called
5. **Function detects chat query context**
6. **Uses user-selected model (e.g., gpt-5-mini)**
7. Reasoning model generates thoughtful response
8. Context reset to None
